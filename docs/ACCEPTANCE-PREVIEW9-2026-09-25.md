# 0.1.0-preview.9 容量不足・受入検証（2026-09-25）

GitHub Actionsの専用Windows Server 2025環境で、固定256 MiBのVHDを新規作成し、NTFSの空き容量を実際に0バイトにしました。試験用の書込はWindowsの容量不足エラー112（HResult 0x80070070）で失敗し、容量を戻した後は再開できました。7項目すべて成功し、VHDの切り離し・削除も確認済みです。通常の保存先やユーザーの履歴を使っていません。

対象コミット: 127adfa767f5396d5937a529083372ce5da9e5aa。タグ: v0.1.0-preview.9。
[タグCI](https://github.com/adachi6k/JTCStamper/actions/runs/36149069853)と[main CI](https://github.com/adachi6k/JTCStamper/actions/runs/36148644994)で成功しました。

## 実容量不足の結果

|対象|結果|
|---|---|
|初回鍵保存|容量不足で失敗し、不完全なkey.dpapiを確定しない。容量回復後に作成・再読込できる|
|Generated保存|コピー0回、残る記録0件。回復後に再生成できる|
|CopyRequested保存|コピー0回、残る記録1件。回復後も既存記録のHMACを保持|
|CopyCompleted保存|コピー先呼出1回、残る記録2件。完了記録を作らず、回復後に再生成できる|
|原本・バックアップの上書き|既存ファイルの全バイトを保持。回復後に保存し、バックアップ復元・履歴認証も成功|
|画面のコピー前|成功と表示せず、コピー先を呼ばない。回復後は再実行できる|
|画面のコピー後|保存失敗を成功と扱わず、回復後の再実行と履歴認証に成功|

各書込時の容量不足エラーと空き容量はdisk-full-preview9-2026-09-25.jsonに記録しました。画面試験ではMainWindow.CopyAsyncの失敗戻り値、エラー表示、履歴、回復を検査します。クリップボードは全容量不足試験で専用のダミーを使い、Windowsクリップボード自体を満杯時に操作する試験ではありません。原本はGUIのファイル選択ではなく、同じ署名済み記録をAtomicFileで書く経路です。

例外注入による6条件（3段階×エラー39/112）もCoreテストへ追加しました。こちらは実容量不足とは別の検査です。コピー処理の追記境界をIJournalWriterへ分離し、通常のアプリは従来どおりJournalを使用します。試験側だけが指定の追記直前にVHDを満杯にし、その後は実際のJournal.Appendを呼び出します。

NTFSは小さなファイルを管理領域に格納できるため、空き容量表示だけでは失敗を保証しません。試験は対象ディレクトリの一時ファイル作成も容量不足になる状態を作り、実際のアプリ側の失敗を確認しています。手順と保護条件は[DISK-FULL.md](DISK-FULL.md)に記載しました。
