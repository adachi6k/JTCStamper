# 円周＋横線4か所の色コードと16ビット化の比較

## 結論

横線の4か所を各1ビットとして追加することで、識別情報を12ビット（4,096通り）から16ビット（65,536通り）へ増やす試験実装ができました。16ビット案は未使用32種類の値でも、白背景の88px/176px PNGを全件正しく復号しました。

ただし、88px JPEGでは円周の色変化が弱くなり、円周の欠けを残す案でも復号率は低下しました。製品の12ビット方式・配布EXEは変更していません。今回の成果は実験用生成器・読取器・比較結果です。16ビットが安定して運用できると実証したわけではありません。

## 配置と容量

| 方式 | 円周のセル | 横線のセル | 識別情報 | 付加情報 | 合計セル |
|---|---:|---:|---:|---:|---:|
| ring12：円周の色のみ | 28 | 0 | 12 bit | マーカー8＋CRC8 | 28 |
| split12：円周と横線の色に分散 | 24 | 4 | 12 bit | マーカー8＋CRC8 | 28 |
| split16：円周と横線の色で増量 | 28 | 4 | 16 bit | マーカー8＋CRC8 | 32 |
| hybrid16：円周の欠け＋横線の色 | 28 | 4 | 16 bit | マーカー8＋CRC8 | 32 |

12ビットから16ビットへの増量は4ビット、識別値の数は16倍です。横線4か所がすべて同じ色になる値もあるため、見える色変化の数はコードごとに変わります。32セル全部が識別情報ではありません。

赤RGB(195,32,40)と朱色RGB(220,75,30)を使用。色は完全不透明とし、3つの色方式では赤基調／朱色基調を入れ替えて比較しました。hybrid16は赤基調のみ。円周の1セルは3.5度、37〜143度と217〜323度に等間隔で配置します。split12は各12セル、その他は各14セルです。

横線は上段・下段の各左右に2か所、合計4か所。96単位の設計座標で中心から線に沿って±24、区間長6（直径88pxで約5.5px）とし、それ以外の線には情報を追加しません。1ビット＝基調色／差し色の2状態です。色を区別しやすくするため、今回これ以上短くしていません。

横線の相対角度は従来どおりコードの下位2ビットから決めています。独立した追加情報ではないため、これを足して18ビットとは数えていません。4色化による20ビット等も未検証です。

## 符号・検査・読取

形式マーカーはring12=0xD3、split12=0xD4、split16=0xD5、hybrid16=0xD6。CRC-8は多項式0x07・初期値0で、マーカー、全ペイロードの高位バイト、低位バイトの順に計算します。横線のビットもCRCの対象です。

円周にマーカー、ペイロード下位（ring12:12／split12:8／split16・hybrid16:12ビット）、CRCをMSBから配置し、横線4セルへペイロードの上位4ビットを上左・上右・下左・下右の順に配置します。完全なイベントIDではなく、履歴候補用の短い値です。CRCは誤り検出であり訂正や暗号学的認証ではありません。

読取側には方式だけを指定し、正解コード・生成パレット・履歴候補は渡しません。元画像から赤い円形領域を探索し、±8度を0.25度刻み、中心±0.5pxで調べます。色方式は(G−B)/(R−(G+B)/2)の比を円周マーカーで校正し、色差0.10以上とセル境界の余裕を要求します。hybrid16は円周の濃淡を読み、横線の色を各区間の前後の基調色と比較します。複数の異なるコードが得られれば棄却します。

全4方式の139,264値で符号化→復号を確認。各セルを1つずつ反転した4,423,680条件はすべて棄却しました。これは符号処理の検査であり、全65,536値の画像耐性を検査したものではありません。

## 合成画像による開発用比較

Pillowの独立描画を8倍サイズから縮小し、PNG相当／JPEG品質80を評価しました。1方式・パレットにつき符号付き792条件、符号なしの対照132条件。7構成合計6,468条件です。

白背景はJTC/田中、6コード、88/176px、回転−4/0/4度、画素位置−0.35/0/+0.35px。背景追加は黄・青・灰・黒文字・赤文字とし、田中、画素位置+0.35pxを使用。12ビットの値は0、1、0x555、0xAAA、0xBCD、0xFFF。16ビットの値は0、1、0x5555、0xAAAA、0xABCD、0xFFFFです。

白背景の正解数（各108件）：

| 方式 | 基調色 | 88px PNG | 88px JPEG | 176px PNG | 176px JPEG |
|---|---|---:|---:|---:|---:|
| ring12 | 赤 | 108/108 | 0/108 | 108/108 | 11/108 |
| ring12 | 朱色 | 108/108 | 0/108 | 108/108 | 1/108 |
| split12 | 赤 | 108/108 | 0/108 | 108/108 | 7/108 |
| split12 | 朱色 | 108/108 | 0/108 | 108/108 | 6/108 |
| split16 | 赤 | 108/108 | 0/108 | 108/108 | 2/108 |
| split16 | 朱色 | 108/108 | 0/108 | 108/108 | 4/108 |
| hybrid16 | 赤 | 108/108 | 23/108 | 108/108 | 84/108 |

背景を含む全条件（各792件）では以下の結果でした。読めなかった件を正解に含めません。

| 方式 | 基調色 | 正解 | 判定不能 | 誤コード |
|---|---|---:|---:|---:|
| ring12 | red | 384 | 407 | 1 |
| ring12 | vermilion | 372 | 420 | 0 |
| split12 | red | 381 | 411 | 0 |
| split12 | vermilion | 376 | 416 | 0 |
| split16 | red | 369 | 423 | 0 |
| split16 | vermilion | 371 | 421 | 0 |
| hybrid16 | red | 521 | 271 | 0 |

赤基調ring12の灰背景・176px・−4度・JPEG（00703.bgra）で、正解0x555を0xD00と誤読した1件があります。CRCを通ったため、誤読を完全に防げる方式とは扱いません。符号なし対照は全924条件でコード分類0件ですが、構成間で重複した対照を含み、模倣一般の誤受入率ではありません。

## 未使用32値による追加評価

開発用6値を除き、固定シード20260918で32値を選択。各値を白背景・88/176px・PNG/JPEGで評価し、split16赤基調とhybrid16を比較しました（256条件）。氏名・回転・画素位置は固定順で変化させています。復号器はこの結果を見る前に固定し、追加評価後の閾値変更はしていません。同じ描画器による合成画像なので、実環境に対する独立検証ではありません。

| 方式 | 88px PNG | 88px JPEG | 176px PNG | 176px JPEG |
|---|---:|---:|---:|---:|
| split16 | 32/32 | 0/32 | 32/32 | 1/32 |
| hybrid16 | 32/32 | 2/32 | 32/32 | 27/32 |

追加評価では両方式とも誤コード0件で、残りは判定不能でした。PNGでは16ビット化が機能していますが、88px JPEGでは横線だけを色にしても十分な耐性が得られていません。176px JPEGはhybrid16で27/32件に改善しました。

## 適用範囲と次の判断

今回は6,724条件の合成画像評価です。Windows WPF・Office・EMF・実印刷・スキャンでは未検証です。模倣画像の誤受入率、画像からの真正性、無断コピーの識別は評価していません。12ビットや16ビットの値とCRCを模倣できる点は変わりません。

横線4か所で容量を増やす構成は可能です。PNGの経路を確保できる用途では16ビット案を次の実機評価候補にできます。小さいJPEGも対象にする場合は、色差だけに依存せず横線の形状変化等も比較する必要があります。方式の容量だけを理由に製品へ採用せず、誤読・判定不能・見た目の比較を続けます。製品は引き続きwpf-v5-gap12です。

## 再現

.NET 10 SDK、Python＋Pillow、Yu Gothic Regularのフォントが必要です。画像データ生成に約1.5GBの空き容量を使います。

```text
python scripts/Generate-ColorLineFixtures.py <開発画像フォルダー> <YuGothR.ttc>
dotnet run --project tests/JTCStamper.ColorLineEvaluation -c Release -- --check-codec
dotnet run --project tests/JTCStamper.ColorLineEvaluation -c Release -- <開発画像フォルダー>/manifest.json <開発結果.json>
python scripts/Generate-ColorLineFixtures.py <追加画像フォルダー> <YuGothR.ttc> --holdout
dotnet run --project tests/JTCStamper.ColorLineEvaluation -c Release -- <追加画像フォルダー>/manifest.json <追加結果.json>
```

終了コード0は評価の完了を意味し、製品への適合や真正性の合格ではありません。結果JSONのCorrect・Wrong・Unreadable・ControlClassifiedを確認してください。判定不能を正しい復号と数えません。描画方式を自動選択する製品UIや、新形式での履歴保存・コピー処理は今回の実験には含めていません。
